## 2. Primary source — Advanced Tool Use

**Publisher:** Anthropic  
**Source:** https://www.anthropic.com/engineering/advanced-tool-use

### Relevant section: Tool Search trade-off

Anthropic explicitly says tool search adds a search step before invocation and therefore should be used when its context/accuracy benefit outweighs the additional latency.

Short excerpt:

> “enabling the Tool Search Tool involves trade-offs”

This is a direct example of the exam objective: a configuration can improve context efficiency and tool-selection accuracy while adding another step.

### Relevant section: programmatic tool calling

Anthropic describes programmatic tool calling as a way to process intermediate tool results in code rather than sending every result through additional model turns.

This supports:
- reducing model round-trips;
- controlling how much intermediate data enters context;
- using architecture changes to improve efficiency.

## 3. Primary source — Contextual Retrieval

**Publisher:** Anthropic  
**Source:** https://www.anthropic.com/engineering/contextual-retrieval

### Relevant section: reranking

Anthropic evaluates retrieval approaches that include semantic retrieval, BM25, rank fusion, and reranking.

Reranking can improve retrieval quality, but it adds another processing stage.

This supports the general trade-off:

```text
additional retrieval/ranking work
↔ additional quality potential
↔ additional latency/cost
```

The source demonstrates that retrieval architecture should be evaluated empirically rather than assuming every stage is always necessary.

## 6. Current D3.3 note under review

### Core idea

Every extra retrieval step, reranker, model call, tool call, or verification stage adds latency. Keep stages that provide **measurable quality value**.

### What you need to know

```text
request
+ retrieval
+ reranking
+ model inference
+ tool calls
+ verification
= end-to-end latency
```

Track percentiles such as p95/p99, not only averages.

Parallelize truly independent work. Do not parallelize steps with hidden dependencies.

### Decision rules

- Add a quality-enhancing stage only when the measured improvement justifies its latency and cost.
- Optimize the dominant contributor rather than the easiest component to tweak.

### Common traps

- Adding reranking merely because it is available.
- Measuring average latency only.
- Parallelizing dependent calls and creating race conditions.
- Lowering latency by removing a required safety check.
