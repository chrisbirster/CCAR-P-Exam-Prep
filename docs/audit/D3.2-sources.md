## 3. Primary source — MCP Apps Authorization

**Publisher:** Model Context Protocol ecosystem documentation

### Relevant section: OAuth-based authorization

Short excerpt:

> “MCP Apps can protect tools behind OAuth-based authorization”

The page describes both:
- per-server authorization;
- per-tool authorization.

It requires token discovery/verification for protected resources.

This strongly supports:
- authentication/identity being established through trusted authorization infrastructure;
- protected tools being gated outside the model's natural-language output.

### Relevant section: HTTP-boundary enforcement

The documentation explains that protected calls are checked before reaching the MCP tool handler.

Short excerpt:

> “authorization is enforced at the HTTP boundary”

This strongly supports our study-note rule that protected actions should not depend on the model declaring that access is allowed.

### Relevant section: token verification and user identity

The page describes verifying access tokens, extracting authenticated user identity, and passing that auth context into request handling.

This supports:
- preserving trusted identity through the tool call;
- scoping tool behavior to the authenticated caller.

### Relevant section: defence in depth

The page recommends verifying auth context inside protected tool handlers as an additional safeguard even when the HTTP layer already enforces authorization.

This supports:
- layered enforcement;
- re-checking protected operations at meaningful boundaries.

## 7. Current D3.2 note under review

### Core idea

**Authentication proves identity. Authorization determines permitted actions.** The model should not invent either.

### What you need to know

A secure tool call should preserve trusted identity through the request path.

```text
user authenticates
→ application establishes trusted identity
→ policy determines allowed capability
→ model proposes action
→ deterministic layer authorizes action
→ tool executes under scoped credentials
→ audit record captures actor/action/result
```

User text such as “I am an administrator” is not authentication.

A model statement such as “the user is allowed to do this” is not authorization unless the model is merely reporting a decision produced by an authoritative policy system.

For multi-tenant systems, authorization must also enforce tenant boundaries.

### Decision rules

- Establish identity before the LLM decision layer.
- Keep authorization close to the protected resource/action.
- Use scoped/delegated credentials when acting for a user.
- Re-check authorization for consequential tool calls.
- Record who initiated the action and which identity actually executed it.

### Common traps

- Passing a user role as prompt text and trusting it.
- Using one backend superuser credential for every tenant.
- Letting the model decide access policy.
- Authenticating once but never checking action-level permissions.
