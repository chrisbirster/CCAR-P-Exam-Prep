## 2. Primary source — Contextual Retrieval

**Publisher:** Anthropic  
**Source:** https://www.anthropic.com/engineering/contextual-retrieval

### Relevant section: Retrieval-Augmented Generation

Anthropic defines the basic RAG pattern as retrieving relevant information from a knowledge base and adding it to the model's prompt.

Short excerpt:

> “retrieves relevant information from a knowledge base”

This establishes the core D3.5 concept.

### Relevant section: standard retrieval flow

Anthropic's example RAG flow includes:

1. splitting documents into chunks;
2. producing lexical/semantic representations;
3. BM25 exact-match retrieval;
4. embedding-based semantic retrieval;
5. combining/deduplicating results with rank fusion;
6. adding top chunks to the prompt.

This directly supports much of our RAG pipeline.

### Relevant section: chunking problem

Anthropic explains that splitting documents into chunks can destroy important surrounding context, making a relevant chunk harder to retrieve or interpret.

This supports:
- treating chunking as an architectural decision;
- evaluating whether chunks preserve enough meaning.

### Relevant section: contextualized chunks

Anthropic's Contextual Retrieval adds concise document-level context to each chunk before building semantic and BM25 indexes.

This supports:
- enriching indexed chunks;
- designing ingestion/indexing for better retrieval quality.

### Relevant section: reranking

The article discusses combining retrieval approaches and evaluates reranking as an additional relevance-improvement stage.

This supports reranking as an optional pipeline stage.

## 4. Important audit point

Our pipeline is a **useful synthesized production pipeline**, but we should not teach:

> “Anthropic defines RAG as exactly these 12 stages.”

It does not.

The flashcard-safe distinction is:

- **direct fact:** RAG retrieves relevant knowledge and places it in model context;
- **direct fact:** chunking/indexing/retrieval strategy affect retrieval quality;
- **direct fact:** semantic + lexical retrieval and reranking are valid techniques;
- **our design guidance:** metadata, query transformation, permission filtering, and grounding/citation checks may be added as requirements demand.

## 5. Current D3.5 note under review

### Core idea

RAG is a pipeline for selecting relevant external knowledge and placing it in context at inference time.

### Pipeline

```text
source ingestion
→ parsing
→ chunking
→ metadata enrichment
→ indexing
→ query transformation (optional)
→ retrieval
→ metadata filtering
→ reranking (optional)
→ context assembly
→ generation
→ grounding/citation checks
```

### Decision rules

- Start with the simplest pipeline that meets retrieval quality.
- Measure retrieval separately from generation.
- If the relevant evidence is never retrieved, prompt changes cannot fix the missing evidence.

### Common traps

- Treating RAG as synonymous with a vector database.
- Ignoring document permissions.
- Mixing obsolete/current content without freshness controls.
- Debugging retrieval failure solely by rewriting the prompt.
