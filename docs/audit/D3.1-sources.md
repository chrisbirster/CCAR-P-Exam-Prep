## 2. Primary source — Writing Effective Tools for AI Agents

**Publisher:** Anthropic  
**Published:** September 11, 2025  
**Source:** https://www.anthropic.com/engineering/writing-tools-for-agents

### Relevant section: “Choosing the right tools for agents”

Anthropic explains that simply exposing more tools does not automatically improve an agent.

Short excerpt:

> “More tools don’t always lead to better outcomes.”

The surrounding section explains that tools should be intentionally chosen for agent use instead of mechanically wrapping every existing API endpoint.

This directly supports our note's idea that:
- an agent should not receive every available tool by default;
- tool exposure should be selective;
- capability should be designed around the task.

### Relevant section: clear and distinct tool purposes

Anthropic recommends that each tool have a clear and distinct purpose.

The article gives the example that a higher-level tool can sometimes be better than several low-level tools when it reduces irrelevant intermediate context and maps more naturally to the agent's task.

This supports:
- minimizing redundant tool surfaces;
- favoring useful task boundaries;
- avoiding capability that adds little value.

### Relevant section: overlapping tools

Short excerpt:

> “Too many tools or overlapping tools can also distract agents”

Anthropic explains that overlapping functionality can make it harder for the model to choose an efficient strategy.

This directly supports our note's claim:

> Too many similar tools can reduce accuracy because the model must choose among overlapping definitions.

### Relevant section: “Namespacing your tools”

Anthropic says agents may encounter dozens of MCP servers and hundreds of tools. When tools overlap or have vague purposes, agents can become confused about which one to use.

This supports:
- clear tool boundaries;
- distinct names/purposes;
- reducing unnecessary overlap.

### What this source does NOT establish

This article does not define a formal security doctrine called “capability bloat.”

It is mainly about:
- tool ergonomics;
- tool-selection quality;
- context efficiency;
- evaluation-driven tool design.

Our security/least-privilege claims therefore need additional evidence.

## 3. Primary source — How We Contain Claude Across Products

**Publisher:** Anthropic  
**Published:** May 25, 2026  
**Source:** https://www.anthropic.com/engineering/how-we-contain-claude

### Relevant section: blast radius grows with capability and access

Short excerpt:

> “As agents grow more capable, so does their potential blast radius.”

Anthropic explains that agent risk has two dimensions:
- how likely something is to fail or be compromised;
- how much damage is possible if that happens.

The article says the theoretical blast radius grows as capabilities and access expand.

This directly supports:
- reducing unnecessary capability;
- minimizing unnecessary credentials/access;
- thinking about side effects and environment access as part of agent risk.

### Relevant section: containment at the environment layer

Anthropic describes process sandboxes, VMs, filesystem boundaries, and egress controls as ways to enforce hard limits on what an agent can reach.

A key example is that credentials outside the sandbox cannot be exfiltrated by the agent.

This supports our note's emphasis on:
- credentials available to the runtime;
- environments the agent can access;
- hard boundaries rather than prompt-only restrictions.

### Relevant section: broad capability can still be appropriate

Anthropic also explains that Claude Code needs filesystem, shell, and network access to be useful as a coding agent.

This is important because it prevents an overly simplistic rule such as:

> Broad tools are always bad.

The better rule is:

> Give broad capability only when the use case requires it, then constrain its environment and permissions.

This is why our audited D3.1 wording says:

> Prefer bounded, task-level tools when the use case does not require general-purpose capability. When broad tools are necessary, constrain their environment, credentials, and permissions.

### Relevant section: logs are not sufficient prevention

The article describes cases where a poisoned tool result can lead to an apparently authorized API call, meaning logs may show a successful action after the damage has already occurred.

That supports our “common trap”:

> “It's safe because all actions are logged.”

Logging helps detection and reconstruction, but it does not replace capability restriction or containment.

## 4. Primary source — Effective Context Engineering for AI Agents

**Publisher:** Anthropic  
**Published:** September 29, 2025  
**Source:** https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### Relevant section: context is finite

Short excerpt:

> “Context is a critical but finite resource for AI agents.”

Anthropic frames context engineering as choosing the most useful information for the model rather than loading everything that might possibly be relevant.

This supports the context-cost side of capability bloat:
- every tool definition consumes context;
- unnecessary context can reduce signal;
- more visible capability is not automatically better.

### Relevant section: smallest useful context

Anthropic recommends selecting the smallest useful set of high-signal tokens that maximizes the likelihood of the desired behavior.

This supports:
- avoiding unnecessary tool definitions;
- avoiding irrelevant data in the model's active context;
- progressive/context-aware exposure of capability.

### What this source does NOT establish

This source is primarily about context management, not permissions.

It strengthens the **decision/context-bloat** part of D3.1 but should not be used by itself to justify authentication, authorization, or sandboxing claims.

## 6. Current D3.1 note under review

### Core idea

Every tool, credential, dataset, and side effect exposed to an agent expands both the **decision surface** and the **attack surface**.

### What you need to know

Least privilege for an agent means minimizing:

- tools it can discover;
- operations each tool permits;
- data each tool can return;
- credentials available to the runtime;
- environments it can access;
- side effects it can execute without approval.

Too many similar tools can also reduce accuracy because the model must choose among overlapping definitions.

Anthropic's tool-design guidance stresses choosing the right tools—not simply exposing everything—and current advanced tool-use guidance supports on-demand discovery to avoid huge tool-definition contexts.

### Decision rules

- Give the model the smallest capability set that can accomplish the task.
- Separate read and write tools when their risk differs.
- Prefer bounded, task-level tools when the use case does not require general-purpose capability.
- When broad tools are necessary, constrain their environment, credentials, and permissions.

### Common traps

- “It's safe because all actions are logged.”
- “The model needs every tool in case it becomes useful.”
- One shared admin credential for all users.
- Exposing raw database access when a scoped business API would suffice.

### Scenario

A support assistant needs order status and refund requests. It should not receive a generic database-write tool when two scoped tools can expose exactly those operations.
