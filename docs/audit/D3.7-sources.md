## 2. Primary source — Model Context Protocol Specification

**Publisher:** Model Context Protocol  
**Current specification observed:** 2026-07-28  
**Source:** https://modelcontextprotocol.io/specification/

### Relevant section: what MCP is

Short excerpt:

> “MCP is an open protocol”

The specification says MCP standardizes integration between LLM applications and external data sources/tools.

This directly supports:
- MCP as a standardized integration mechanism;
- reusable tool/context surfaces across compatible hosts/clients.

### Relevant section: protocol roles

The spec defines:
- hosts;
- clients;
- servers.

Servers provide context/capabilities such as:
- resources;
- prompts;
- tools.

This helps distinguish MCP from simply calling an ordinary private function directly.

### Relevant section: capability discovery / negotiation

MCP includes capability negotiation and standardized server features.

This supports using MCP where interoperability/discovery across compatible AI clients matters.

### Relevant section: security

The MCP specification explicitly warns that arbitrary data access and code execution require access controls, consent, and security best practices.

This directly supports:

> MCP does not replace authorization or application security.

## 3. API / SDK / CLI

The exam objective itself requires comparing MCP with API/CLI-style integrations.

Our decision guidance is architecture interpretation:

**Direct API/SDK is often sensible when:**
- one application owns the integration;
- the interface is narrow;
- reuse across AI clients is not needed;
- a protocol adapter would add unnecessary operational surface.

**CLI is often sensible when:**
- an existing CLI is already a stable developer/ops interface;
- local tooling and automation are central;
- the execution environment naturally uses command-line workflows.

These are decision heuristics, not MCP specification requirements.

## 4. Agent-to-agent communication

The reproduced exam objective explicitly includes agent-to-agent as a category to compare.

Our note says it is useful when independent agent systems have separate responsibilities and require explicit handoffs.

That is architecture interpretation consistent with multi-agent design, but it is not established by the MCP specification itself.

- agent-to-agent communication;

It recommends choosing based on:

- number/type of clients;
- interface ownership;
- reuse requirements;
- authorization boundary;
- operational complexity.

### Common traps

- Choosing MCP merely because Claude is involved.
- Assuming MCP tools are automatically secure.
- Adding a protocol boundary when a simple private API/function is sufficient.
- Creating agent-to-agent coordination where a simpler tool boundary works.
